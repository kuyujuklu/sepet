# Bump targetSdk/compileSdk to 36 (Android 16)

Date: 2026-09-01
Scope: `app` only.

## What & why

Google Play requires new app updates to target API 36 (Android 16) as of 2026-08-31 -
that deadline already passed by the time this was done. The last uploaded bundle
(#66, per Play Console's "Наборы App Bundle" screen) still targets API 35, so the next
upload (the one with the Firebase Analytics fix) needed this bump to actually be
acceptable, not just for future-proofing.

## Files

### Modified

- `app.json` - `expo-build-properties` plugin's `android` block:
  `compileSdkVersion`/`targetSdkVersion` 35 → 36, `buildToolsVersion` "35.0.0" →
  "36.0.0". SDK 53's own default `compileSdkVersion` is 35, hence the explicit
  override was already there and just needed the number changed.

## How it works

`expo-build-properties` patches the generated native Android project during EAS
Build's prebuild step - no other config or code path reads these values, so this is
the entire change.

## Backend gaps

None - client build configuration only.

## Known limits / follow-ups

- **Confirmed successful** - `eas build --profile production --platform android`
  (build `6210c3b7`, `appBuildVersion` 71) finished clean: Gradle log shows
  `compileSdk: 36` applied everywhere, including
  `:react-native-firebase_analytics:android.compileSdk using custom value: 36` and
  the same for `_app`, and `BUILD SUCCESSFUL in 15m 24s`. One non-blocking warning:
  "This Android Gradle plugin (8.8.2) was tested up to compileSdk = 35" - AGP 8.8.2
  is what RN 0.79.5/Expo 53 ships, it just isn't officially validated against 36 yet,
  but it built and ran fine here. Re-verified the Firebase Analytics classes are
  still in the resulting `.aab` the same way as the earlier Android checks.
- **Android 16 behavior changes are enforced by the OS based on targetSdkVersion,
  not opt-in.** Researched what's relevant to this app specifically:
  - Edge-to-edge can no longer be opted out of. `app.json` already has
    `edgeToEdgeEnabled: true` and there's a prior fix
    (`2026-08-27-android-navbar-icon-contrast.md`) for the nav-bar icon contrast
    that edge-to-edge caused - worth a quick re-check on a real device once the
    build is up, but nothing here suggests it's newly broken.
  - Predictive back gesture is enforced more aggressively. This app doesn't
    override `onBackPressed`/intercept the back gesture anywhere I've seen; should
    be fine, not independently verified on-device.
  - **16 KB native memory page size.** Apps with native code (this one has several -
    Hermes, `@react-native-firebase/*`, others) need their native libraries built
    16 KB-aligned. EAS Build's managed NDK is expected to already produce
    16 KB-aligned `.so` files for current SDK builds, but this wasn't
    independently verified - if Play Console's pre-launch report flags 16 KB
    compatibility after upload, that's the next thing to chase.
  - React Native itself only started *defaulting* to targeting Android 16 at
    **RN 0.81** (per RN's own 0.81 release notes); this project is on **0.79.5**
    (see `2026-08-31-firebase-analytics-sink.md` for why it's pinned there -
    `@react-native-firebase` 26.x needs RN 0.81's CMake API, which is the same RN
    version boundary). So this app is targeting API 36 on an RN core one minor
    behind what Google's own ecosystem treats as the "designed for 36" baseline -
    plausible but not something either RN or Expo has explicitly certified for
    this combination. Worth keeping in mind if anything OS-behavior-related looks
    off after this ships.

## 2026-09-02 (later): both addressed

**R8/ProGuard**: enabled `enableProguardInReleaseBuilds` +
`enableShrinkResourcesInReleaseBuilds` in `expo-build-properties`'s `android` block.
This app's own JS/native code needed nothing special - the realistic risk was always
third-party native modules missing consumer ProGuard rules, not app code. Verified
with a real `eas build --profile production --platform android` (not just
`expo export`, since R8 issues live in the compiled DEX, invisible to a JS bundle
check) - see result below.

**Edge-to-edge**: turned out to already be resolved as a side effect of the SDK 54
upgrade, not something to hand-fix. Checked `node_modules` before/after: the
`react-native-edge-to-edge` package (present and autolinked under SDK 53/RN 0.79 -
it's what emitted the `react-native-edge-to-edge:checkKotlinGradlePluginConfiguration
Errors` line in the very first CMake-failure build log) **is gone entirely** on SDK 54
- RN 0.81 has edge-to-edge support built into core RN now, so Expo stopped pulling in
the community polyfill. Whatever legacy/deprecated API calls Play's scanner was
objecting to almost certainly lived inside that now-absent package. Not able to
fully confirm without a real Play Console re-scan after this build is uploaded (that's
on the user, Play doesn't expose that check to a CLI), but this is strong enough
evidence to treat it as resolved rather than going looking for a separate fix.

**Result: confirmed.** `eas build --profile production --platform android` (build
`885fcf40`, `appBuildVersion` 73) finished clean with both `app.json` R8 flags and the
SDK 54 upgrade together. Downloaded the `.aab` and compared it directly against the
pre-R8 build: dex payload dropped from 3-4 files totaling ~24 MB down to **2 files,
~11.3 MB total** - strong evidence R8 shrinking is genuinely active, not just enabled
and silently no-op'ing. `com/google/firebase/analytics/FirebaseAnalytics` is still
present with its normal (unobfuscated) name, confirming Firebase's own consumer
keep-rules protected its public API as expected.

**Residual, unverifiable-from-here risk:** R8 can still break something that's only
reached via runtime reflection (`Class.forName`-style dynamic lookups) rather than a
static reference R8's analysis would catch - that class of bug wouldn't show up as a
build failure, only as an on-device crash in that specific code path. The build
succeeding and Firebase working is a good sign but not a full guarantee; worth an
actual device smoke-test (not just this repo's usual `expo export`/build-succeeded
checks) before this ships to Play, specifically around anything unusual/dynamic - push
notifications, deep links, and any native module invoked conditionally are the classic
places R8-only-at-runtime breakage tends to hide.
